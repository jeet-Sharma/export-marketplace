1. Purpose and Scope
This document defines the proposed Phase 1 relational data model for the Export Marketplace Platform. It translates the approved Phase 1 product-management and public-catalogue requirements into a PostgreSQL-oriented schema.
Public marketplace exposes only PUBLISHED products.
Authorized Platform Users create and manage products.
Products may be saved as DRAFT and published later.
Publishing makes a product publicly visible immediately in Phase 1.
Unpublishing returns the product to DRAFT.
Role/permission tables provide a foundation for configurable platform access.
Vendor self-service registration/login, Buyer, RFQ, Order, Payment, Inventory, Logistics and advanced Compliance tables are intentionally excluded from Phase 1. A minimal vendors master is included because products are assigned to suppliers.
Note: Some field-level decisions remain open in the BRD/PRD. These are marked TBD rather than silently treated as final requirements.

Use status rather than hard-deleting operational users where possible.
created_at and updated_at should use timezone-aware timestamps.

5.8 vendors
Stores the minimal supplier/vendor master required by the Add Product UI. In Phase 1, Platform Users select a supplier when creating or editing a product. This does not introduce Vendor Portal, Vendor login, KYC, Maker/Checker or vendor-managed product workflows.
Business / modeling notes
Treat Supplier and Vendor as the same Phase 1 business entity unless the Product Manager defines them separately.
A vendor can supply many products; each Phase 1 product references one vendor/supplier.
Use ACTIVE / INACTIVE status for catalogue selection. Do not label a supplier as verified unless verification requirements are explicitly approved.
Future Vendor registration/login can reuse this master by setting users.vendor_id to the Vendor. KYC, approval and Maker/Checker workflows can then be added without changing products.vendor_id.

8. Delete and Referential-Integrity Strategy
Product deletion behavior is still an open business decision. Until confirmed, prefer unpublish over permanent deletion.
Child records such as product_images, product_price_tiers and product_countries can use cascade deletion only if permanent product deletion is formally approved.
Reference/master records such as categories and countries should normally be deactivated instead of deleted when already referenced.
Users referenced by audit fields should not be physically deleted without an explicit retention/anonymization strategy.
9. AWS S3 Image Storage
PostgreSQL stores product-image metadata; AWS S3 stores the image objects. The backend can create upload/access URLs as appropriate. The database should keep stable object keys rather than temporary signed URLs.
products   |   +---- product_images.s3_object_key                         |                         v                    AWS S3 Bucket
10. Phase 1 Public Query Boundary
The public catalogue boundary must enforce publication status at the backend/service/query layer.
Public Product Listing:WHERE products.status = 'PUBLISHED'Public Product Detail:WHERE products.slug = :slug  AND products.status = 'PUBLISHED'Admin / authorized Platform User:May access DRAFT and PUBLISHED subject to permission checks.
Note: UI filtering alone is not a security or publication boundary. Draft exclusion must be enforced server-side.
11. Future Extension Points - Not Phase 1 Tables
Future domain
How Phase 1 stays extensible
Vendor / Supplier
A minimal vendors master and products.vendor_id exist in Phase 1. users.vendor_id is nullable and can connect a future Vendor User directly to one Vendor. This supports one Vendor having many Users without a vendor_users table. If one User must later manage multiple Vendors, a junction table can be introduced then.
Buyer
Buyer accounts and organizations can be introduced as a separate domain without changing catalogue fundamentals.
RFQ / Quotations
Can reference product_id, buyer organization and vendor organization when the workflow is approved.
Orders / Payments
Can be introduced as transaction modules after checkout and settlement rules are defined.
Inventory
Can be modeled by product/variant and warehouse once stock ownership and reservation rules are defined.
Logistics
Shipment entities can be added once provider, payer and tracking requirements are approved.
Compliance
Structured country/product compliance rules can replace or supplement Phase 1 informational fields.
Multi-currency / country pricing
A future product_prices or offer/pricing model can be introduced if one base price is insufficient.

Note: Future-ready means preserving clean boundaries, not creating unused future tables now.

14. Implementation Guidance
Use PostgreSQL UUID primary keys consistently.
Create schema changes through versioned database migrations.
Keep NestJS modules aligned with domain boundaries such as auth/access-control and catalog.
Use transactions for multi-table product create/update operations when images, tiers or countries change together.
Validate authorization in the backend, not only in the Next.js UI.
Validate publication requirements in the service/domain layer before setting status to PUBLISHED.
Keep S3 object lifecycle and database metadata synchronized through explicit application flows.
Do not add Vendor Portal/onboarding/KYC tables, Buyer, RFQ, Order or Payment schema until those workflows are defined. The minimal vendors master is included because Phase 1 product onboarding selects a supplier. users.vendor_id is nullable now and supports future Vendor login when needed.
