1. Purpose
This document defines the Phase 1 REST API contract for the Export Marketplace Platform. It covers Platform User authentication, product management, vendor/category/country reference data, product images, bulk pricing, and the public product catalogue.
Public endpoints expose only PUBLISHED products.
Authorized Platform Users manage DRAFT and PUBLISHED products.
A product is associated with one supplier/vendor in the current Phase 1 model.
Shipping, duties and taxes are estimates only; Phase 1 has no live logistics, customs or tax calculation service.
Vendor login/onboarding, Buyer accounts, RFQ, checkout, orders, payments and inventory APIs are outside Phase 1.

The server derives created_by from the authenticated Platform User; clients must not choose arbitrary audit-user IDs.
6.4 PATCH /admin/products/:id
Partially updates a product. If the product is already PUBLISHED, saving valid changes keeps it PUBLISHED under the current Phase 1 rule. If a change would violate mandatory publish requirements, the API should reject the update rather than silently expose invalid public data.

9. Product Image APIs
Product image binaries are stored in AWS S3 and image metadata is stored in product_images. The exact upload implementation may use direct multipart upload or a presigned-S3 flow; the contract should avoid storing temporary signed URLs as permanent database values.
9.1 POST /admin/products/:id/images
Example metadata response{  "id": "uuid",  "productId": "uuid",  "objectKey": "products/<product-id>/<image-id>.jpg",  "isPrimary": true,  "sortOrder": 1,  "altText": "Organic turmeric powder"}
9.2 DELETE /admin/products/:id/images/:imageId
Removes image metadata and coordinates S3 object cleanup according to the selected storage lifecycle strategy.

14. Validation and Business Rules
Only DRAFT and PUBLISHED are valid Phase 1 product statuses.
Public APIs must always enforce status = PUBLISHED.
Publish requires product.publish permission and all finalized mandatory publish fields.
Unpublish requires product.unpublish permission.
vendorId must reference an allowed/active vendor according to the final vendor-status rule.
categoryId, sourceCountryId and targetCountryIds must reference valid active master records.
MOQ and quantities must be positive when supplied.
Prices and estimate values cannot be negative.
Bulk price-tier ranges for a product must not overlap.
Only one primary product image should exist per product when images are present.
createdBy/updatedBy are derived from the authenticated user, not trusted from client input.
Published product edits remain published in Phase 1 if the resulting record still passes publish validation.
15. Security Requirements
Hash passwords using an approved adaptive password-hashing algorithm; never store plaintext passwords.
Use short-lived JWT access tokens and a defined refresh-token/session strategy.
Apply authorization guards to every protected endpoint.
Validate and sanitize DTO inputs using NestJS validation.
Restrict product image type, size and upload behavior.
Do not expose S3 credentials to the browser.
Use HTTPS in deployed environments.
Avoid returning password hashes, internal secrets or sensitive operational metadata.
Apply rate limiting to authentication and other abuse-sensitive endpoints.
Log security-relevant actions without logging secrets/tokens.
16. Non-Functional API Requirements
Use consistent JSON naming conventions across all endpoints.
Use database transactions for product updates spanning products, target countries and price tiers where atomicity is required.
Paginate list endpoints; do not return unbounded catalogue/admin lists.
Add indexes aligned with status/category/vendor/source-country/public-slug queries.
Return stable machine-readable error codes for frontend handling.
Version breaking API changes under the /api/v1 contract.
Keep controllers thin; place business rules in NestJS services/domain logic.
